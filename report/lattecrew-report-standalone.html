先说结论

三个问题的答案

协作有效吗？对正确性有效，对速度和 Claude 额度在小任务上无效。三种方式最后都拿到 175/175 个隐藏测试。Claude 审查在 22 次审查里给出 5 次 CHANGES，找到的都是真实问题：夏令时的墙钟算术、大容量令牌桶的容差、等待时间计算的性能。但 Claude 单独做完 6 道题共 3.4 分钟、折合 API 价 $0.80；Qwen + Claude 用了 70.1 分钟，Claude 审查本身就花了 $0.94。一次审查的固定开销（约 2–3 万 token 的系统提示写缓存）和让 Claude 直接写完这些小题差不多。

能力是下降还是提高？在这组题上没有下降，在边界情况上还略有提高。我把审查者发现的问题写成额外的边界测试，再回头跑三种方式的代码：夏令时那道题，Claude 单独 0/2，Qwen + Claude 1/2，Codex 规划那组 2/2。Codex 的计划里提前点出了夏令时陷阱，Qwen 照着写对了。代价是第一轮实验暴露的脆弱性：OpenCode 输出上限设成 8,192 时，一半的题 Qwen 在一步思考里就把额度用完，什么都没交。

端到端瓶颈在哪？在 Qwen 解码思考 token。Qwen 作业 96% 的时间在生成，生成的 token 里 80% 是思考，解码稳定在约 72 tok/s，预填充几乎全被前缀缓存省掉。其次是三个“每次都要付”的固定成本：模型切换 35–66 秒、Claude Code 每次启动约 3 秒、Kiro 网关每轮重算 4.7 万 token 的提示。网络、SSH、MCP 加起来不到半秒，不是问题。最有效的单项优化是 MTP 推测解码：同一道编程题，开思考时从 77 tok/s 提到 117 tok/s，不损失质量。换 FlashInfer kernel 没有收益，因为解码已经用到约 84% 的显存带宽。

第 1 部分

实验怎么设计的

目标是回答三个问题，所以实验分两类。第一类是逐层的微基准：每一层单独测，固定输入，重复多次取中位数，尽量让上一层的开销不混进下一层。第二类是端到端的协作实验：同一组任务，在不同的分工方式下完整跑一遍，用隐藏测试打分。

可观测性：每层的数据从哪里来

  • 网络和连接层：自写探针 stack_probe.py，测 SSH 新连接与复用、MCP 三种调用方式、scp 1 MB，每项 10–30 次。
  • Agent 层：harness_probe.py 让 Claude Code 和 OpenCode 各回答一句话，读取它们的 JSON 事件流拿到 API 时间和 token；Kiro 层用 kirocrew chat 计时，同时读 vLLM 计数器的差值。为了看清 Kiro 发给模型的内容，我写了一个记录请求体的反向代理。
  • vLLM 层：打开 --enable-mfu-metrics --kv-cache-metrics，从 /metrics 读预填充时间、解码时间、前缀缓存命中的 token 数。流式探针 llm_probe.py 自己测 TTFT 和 TPOT，两边互相印证。
  • GPU 层：nvidia-smi 每 250 ms 采样利用率、显存、功耗、时钟；kernel 级用 vLLM 自带的 torch profiler 抓预填充和解码各一次。
  • 协作实验：crewd 的账本记录每个阶段的秒数和花费；OpenCode 的 step_finish 事件给出每一步的输入、输出、思考 token；Claude Code 的 result 事件给出缓存读写 token 和折算价格；Codex 的 turn.completed 给出计划用的 token。

第 2 部分 · 连接层

Tailscale、SSH、MCP：不是瓶颈

先排除最容易被怀疑的一层。下面每个值都是中位数，单位毫秒。

最慢的是 MCP 每次新开会话：459 ms，而常驻会话里一次调用只要 9.9 ms，差 46 倍。Claude Code 和 Kiro 都会让 MCP 会话常驻，所以实际只在启动时付一次。SSH 隧道让 TTFT 多了约 29 ms，llama-swap 代理只多 1.4 ms。和后面动辄几十秒的模型时间相比，这一层可以忽略。唯一值得做的是确认所有脚本都走 SSH 复用连接（ControlMaster），省下每次约 320 ms。

第 3 部分 · Agent 层

Kiro、Claude Code、OpenCode：固定开销

让每个 agent 只回复一句 “ok”，测的就是它自己的固定开销：启动进程、加载工具、拼系统提示、第一次请求。

Claude Code 一次调用 3.6 秒，其中 API 只有 0.65 秒，剩下约 3 秒是 Node 进程启动、插件和 MCP 初始化。它每次带着 31,376 个 token 的系统提示和工具定义，第一次写缓存，之后读缓存。crewd 每个阶段都起一个新的 Claude Code 进程，所以每次审查都先付这 3 秒和这份缓存读取。

Kiro 的 qwen 网关最反常：回复 “ok” 要 20.7 秒，其中 vLLM 预填充 13.7 秒，而且每一轮的缓存命中都是 0。

为什么 Kiro 每轮都不命中缓存

我在 OpenCode 和 llama-swap 之间加了一个记录请求体的代理，拿到了 Kiro 发给 Qwen 的完整请求。每轮 47,024 个 token 由这些部分组成：107 个工具定义（其中 77 个来自 kirocrew-core MCP，JSON 共 11.8 万字符），一段 2.9 万字符的系统提示（里面列了 19 个同步过来的 skill），最后才是用户消息。

对比相邻两轮的请求，系统提示、工具顺序完全一样，唯一不同的是 OpenCode 内置 bash 工具的描述：它写着本会话的临时目录 …/scratch/cli_chat-fbc438de/opencode，每个 Kiro 会话都不同。Qwen 的聊天模板把工具放在最前面，bash 又是第一个工具，于是两轮请求在第 184 个 token 就分叉了。

混合注意力模型让问题更严重

一般的 Transformer 遇到这种情况，前缀缓存仍能复用分叉点之前的块。Qwen3.8 是混合架构：48 层线性注意力（类似 Mamba 的递推状态）加 16 层全注意力。vLLM 对这类模型用 mamba_cache_mode=align，线性注意力层的状态只在每个调度步的最后一个 token、并且对齐到块边界（这里是 784 token）时才保存。我做了一个对照实验：一个 2.8 万 token 的提示，只改中间一行，结果缓存命中 0 个 token；完全相同的前缀加不同的结尾，命中 28,224 个。也就是说，这个模型只能复用“上一次请求恰好保存了检查点”的位置。

验证：我让代理把描述里带临时目录的工具挪到工具列表末尾，其余不动。前两轮仍是冷启动（还没有可用的检查点），从第三轮起每轮命中 36,848 个 token，预填充从 13.7 秒降到 3.3 秒，整轮从 20.7 秒降到 10.8 秒，快了 1.9 倍。这个代理只是实验用的，没有常驻。要正式修，有三种做法：让 Kiro 或 OpenCode 把会话相关的内容移出工具描述；给 qwen 这个 Bot 少挂 MCP（77 个 kirocrew-core 工具对一个本地编码 Bot 大多用不到）；或者常驻一个小的重排代理。

顺带发现一个配置陷阱。我一度把 OpenCode 的输出上限从 8,192 调到 32,768，Kiro 网关立刻陷入循环：OpenCode 认为可用上下文是 65,536 − 32,768 = 32,768，装不下 4.7 万的提示，于是不停触发“压缩会话”，两轮对话发出了 36 个请求。最后的做法是全局保持 8,192，只在 crewd 起 OpenCode 时用 OPENCODE_CONFIG_CONTENT 单独把输出上限调到 32,768。

第 4 部分 · 推理服务层

vLLM：预填充贵，缓存命中便宜，解码稳定

用流式请求测 Qwen3.8：提示长度从 500 到 6.5 万 token，每个长度 4 次。“冷”是每次加一个随机前缀，强制重算；“命中”是重复同一个提示。输出用 ignore_eos 固定为 256 个 token（最长的一档受上下文上限只能输出约 135 个）。

冷启动时 TTFT 和提示长度成正比，65,401 token 要 20.7 秒；命中缓存只要 298 ms，差 69 倍。所以对 agent 来说，提示长不可怕，提示前缀不稳定才可怕。上一节的 Kiro 就是例子。

解码几乎不受提示长度影响：从 0.5K 到 65K 上下文，TPOT 只从 12.8 ms 涨到 15.4 ms。原因是这个模型 3/4 的层是线性注意力，状态大小固定，只有 16 层全注意力的 KV 随上下文增长。对纯 Transformer，这条线会陡得多。

第 5 部分 · Kernel 与 GPU

Kernel、采样器与推测解码

这一层回答“软件有没有把 GPU 用好”。我对比了三组 kernel 配置，用 torch profiler 抓了一次预填充和一次解码，最后测了模型自带的 MTP 推测解码。每组配置都重启 vLLM，用同一个探针：两档长度的冷预填充各 3 次、512 个 token 的解码 3 次、两路并发。

三组配置的差别都在测量噪声以内（0.5% 左右）。FlashInfer 采样器把 TPOT 从 13.01 ms 降到 12.94 ms；FlashInfer 注意力后端与 FLASH_ATTN 持平。启用它们本身不难：系统没有 nvcc，我用 conda 在用户目录装了 CUDA 13.0 的编译器，再补一个 lib64 软链接，FlashInfer 的 JIT 就能编译通过。但这些 kernel 不在关键路径上。

原因可以从带宽上算出来。每解码一个 token，要把 13.19 GiB 的层权重（AWQ INT4）和 2.37 GiB 的 lm_head（bf16，没有量化）从显存读一遍，合计约 16.7 GB。RTX 5090 的显存带宽是 1,792 GB/s，所以单个序列解码的理论下限约 9.3 ms/token。实测 13.0 ms，已经用到约 72% 的带宽，剩下的还要分给 KV 缓存、线性注意力状态和 kernel 启动间隙。注意力 kernel 只在 16 层全注意力上起作用，换实现自然看不出差别。

这也指出了两个真正有用的方向：一是把 lm_head 量化，它占每步读取量的 15%；二是让一次权重读取产出多个 token，也就是批处理（上一节的 2 并发）和推测解码（下文的 MTP）。

Profiler：时间花在哪些 kernel 上

解码的 profile 把带宽估算落到了实处。63 个解码步在 GPU 上一共 703.6 ms，每步 11.17 ms；端到端 TPOT 是 13.0 ms，所以每步还有约 1.8 ms（14%）是 GPU 之外的时间：调度、采样后处理、和 API 服务的往返。GPU 时间里，INT4 的 Marlin 矩阵乘占 72%，每步约 9.4 ms 读 14.2 GB 权重，折合约 1.5 TB/s，是带宽峰值的 84%；没有量化的 lm_head 单独占 12.5%，每步 1.63 ms。线性注意力（GDN 递推和卷积）只占 3%，全注意力 2.6%，采样 1.2%。这和上面三组配置的结论一致：换注意力或采样 kernel，能改变的只是那几个百分点。

预填充是另一种形态。约 2 万 token 被切成 13 块、每块 1,568 个 token（784 的两倍，正是混合模型要求的块对齐），共 5.4 秒，约 3,840 tok/s。Marlin 矩阵乘占 85%，按 2 × 参数量 × token 数估算，有效算力在 190 TFLOPS 左右，已经是算力受限的量级。FlashAttention 占 9.5%，并且会随提示变长而上升。所以预填充靠 kernel 再挤的空间也有限，靠前缀缓存“不算”才是正解。

MTP 推测解码

Qwen3.8 的权重里带一层 MTP（multi-token prediction）头，vLLM 可以用它当草稿模型：每步先猜后面 k 个 token，再用主模型一次验证。接受率越高，每次前向产出的 token 越多。解码是访存受限的，多验证几个 token 几乎不增加单步时间。我用两种负载测：一种是 t5 题目的真实编程回答（开思考和不开思考），一种是前面用过的“总结代码文件”。

这是整份报告里收益最大的一项。每步猜 3 个 token 时，开思考的编程回答从 77 tok/s 提到 117 tok/s（+52%），不开思考时到 155 tok/s，两路并发的总吞吐从 121 提到 213 tok/s。推测解码由主模型逐个验证，输出分布不变，所以这是不损失质量的提速。

接受率说明了思考内容的特点：不开思考时草稿被接受 90% 左右，开思考时只有 50–75%。思考文本更发散，小的 MTP 头更难猜中。即便如此，猜 3 个仍比猜 1 个快，因为多验证几个 token 几乎不增加一次前向的时间（解码是访存受限的）。

代价是显存：MTP 头和草稿的 KV 让可用 KV 缓存从 139,810 个 token 降到 78,372 个，65K 上下文的请求只能放下 1.2 个。crewd 的 Qwen 作业提示在 1.2–3 万 token，Kiro 网关约 4.7 万，单个请求够用；但如果要同时跑两个长上下文作业，需要把上下文上限降到 32K。

按第 7 部分的时间拆分，Qwen 作业 96% 的时间在解码，其中八成是思考。如果全部换成 MTP-3 的速度，同样的作业预计少用约三分之一的时间。这个推算还没有用完整的协作实验验证。

第 6 部分 · vLLM-Omni

图像、语音、视频：切换比生成贵

三个媒体模型都通过 llama-swap 按需加载，和 Qwen 互斥地用一块 GPU。测法和 media-bot 一样：先拿 GPU 锁，再请求。

切换是这一层最大的成本。生成一张图只要 2.5 秒，但如果 GPU 上正好是 Qwen，要先等 36 秒。TTS 一句话 1 秒，切过来要 66 秒。LatteCrew 的使用模式恰好是交替的：Qwen 在写代码，中间有人要一张图或一段语音。

Z-Image-Turbo

默认 8 步、1024² 一张 4.66 秒，GPU 全程 575 W 满功耗。4 步只要一半时间，对 Slack 里的草图足够。

两个现象。第一，去噪阶段是功耗受限的：功耗贴着 575 W 的上限，时钟只有 2520 MHz。这时提速的手段是减少计算量（更少的步数、更低的分辨率、量化），而不是更好的调度。每步时间随帧数超线性增长：49 帧每步约 2.1 秒，121 帧每步 8.1 秒，帧数 2.5 倍，每步 3.9 倍，符合视频注意力随 token 数平方增长。

第二，去噪结束后有 81 秒 GPU 几乎空闲（利用率个位数、功耗约 50 W）。这段时间包括 VAE 解码、CPU offload 的权重搬运和 MP4 编码。这是纯等待，可以优先排查：如果 VAE 解码被 offload 到了 CPU，把它留在 GPU 上；MP4 编码可以和下一个请求重叠。

第 7 部分 · 协作实验

Codex 规划、Qwen 编码、Claude 审查

这是本报告的核心实验。我在 latte 上建了一个小的 Python 库 ledgerkit，出了 6 道题：两道易、两道中、两道难。每道题有一份只在 Mac 上保存的隐藏测试，共 175 个用例；作业全部结束后，才把测试临时拷到 latte 的临时目录评分，评完删除。三种方式各跑全部 6 道题：

  • Claude 单独：crew task --model sonnet，一个 Claude Code 实例写完、自测、提交。
  • Qwen + Claude 审查：crew local，Qwen 通过 OpenCode 写代码，Claude 只读审查，最多 2 轮，不通过就转人工。

三种方式最终都通过了全部 175 个隐藏测试。差别在时间和额度上：Claude 单独总共 3.4 分钟，Qwen + Claude 用了 70.1 分钟，Codex 规划那组 53.9 分钟。Claude 额度上，协作方式没有省：Claude 单独 $0.80，两种协作方式分别 $0.94 和 $1.03。

原因是审查的固定成本。每次审查都新起一个 Claude Code，带着约 2.2–2.8 万 token 的系统提示和工具定义写缓存，再读 4–8 万 token 的缓存，折合约 $0.10。而这 6 道题都很小，Claude 直接写完一道只要 $0.12–0.14。被打回重做的题要审查两次，就更贵了。t5 有一次审查花了 $0.49：审查者自己写了一个压力测试，跑了 12 分钟，确实找到了一个性能问题。

所以“本地写、云端审”省额度的前提是任务足够大：实现的成本随工作量增长，审查的成本基本固定。之前真实使用中的 crew clean（Qwen 写了 14 分钟、130 万 token）只花了 $0.155 的审查，这类任务才划算。

审查发现了隐藏测试没覆盖的问题

22 次审查里有 5 次 CHANGES，我逐条复现过，全部是真问题：

  • t2 时长解析（Qwen 第一轮，Qwen + Claude 第一次实验）：用 float 累加，parse('0.7d') 得到 60479.99999999999，题目要求整数结果返回 int。第二轮改用 Fraction 后正确。三种方式的最终代码都返回 60480。
  • t4 空闲时段：同一个 ZoneInfo 时区内，Python 按墙钟比较和相减 datetime。夏令时结束那天实际有 25 小时，代码算成 24 小时，min_minutes 过滤就错了。第二轮又发现跨越重复小时的区间会被误判为 end < start。
  • t5 令牌桶：为了消除浮点误差，容差写成 1e-6 × capacity。容量为一百万时，容差就是整整一个令牌，耗尽后还能再取出令牌。
  • t5 令牌桶的另一版：wait_time 每次只加一个 ulp 去逼近，时钟值很大时要循环上百万次。

t2 那条隐藏测试里没有 0.7d 这样的用例，所以第一轮代码也拿了满分。t4 和 t5 的几条超出了题目的明确要求。我把 t4、t5 的问题写成 4 个额外的边界测试，回头去跑三种方式的最终代码：

时间都花在哪

从图 16 能直接看出瓶颈：Qwen 的时间几乎都在几个长的思考步骤上。t4 那次一个步骤思考了 8,898 个 token，用了 124 秒，然后 1 秒内写完文件、跑完测试。按所有 Qwen 作业算，生成速度是 71.8 tok/s，几乎正好等于纯解码速度（TPOT 约 13–14 ms），说明预填充已被前缀缓存消掉，剩下的全是解码。

Codex 的计划把 Qwen 的工作量砍了约四成：生成 token 从 271,656 降到 160,640，总耗时从 70.1 分钟 降到 53.9 分钟，还让 t4 一轮就通过。代价是 Codex 自己读了 295,761 个 token（大部分是缓存）、写了 16,479 个，用的是 ChatGPT 订阅的额度。

第一轮实验：输出上限把一半的题卡死了

第一轮实验用的是当时的配置，OpenCode 的输出上限是 8,192 token。结果两种协作方式都只完成了 3/6：另外 6 次作业，Qwen 在某一步里思考了 8,192 个 token 就被截断，finish_reason 是 length，没有写任何文件。crewd 之前已经加了检查，把这种“干净退出但什么都没说”判为失败，所以没有产生假的“完成”。把 crewd 起 OpenCode 时的输出上限调到 32,768 之后，第二轮 12 次作业全部有结果。上面的主结果用的是第二轮。

第 9 部分

局限

  • 协作实验每种方式每道题只跑了一次（第一轮因配置问题只作参考）。6 道题、175 个隐藏测试足以看出量级上的差别，但不足以对“能力略有提高”下统计意义上的结论。
  • 题目是我出的，规模都很小（几十到两百行）。大任务上本地模型的表现、以及审查成本占比，需要另做实验。
  • Claude 的花费是 Claude Code 报告的 API 折算价。实际用的是订阅额度，折算价反映的是额度消耗的相对大小。
  • Codex 规划在 Mac 上运行，它的 token 用的是 ChatGPT 订阅额度，没有折算成美元。
  • 所有 GPU 测量都在同一台机器上，桌面的 Chrome 和 Xorg 占用约 2 GB 显存，会让 Qwen 的 KV 缓存略小。
  • Wan 去噪后的空闲段，原因是根据功耗和利用率推断的，还没有用 vLLM-Omni 的阶段日志逐项确认。
