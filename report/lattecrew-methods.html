LatteCrew 实验方法

这一页记录《LatteCrew：优化与分析》里每个数字是怎么得到的：测什么、在哪台机器上跑、怎么计时、怎么算，以及脚本的核心代码。代码块都直接摘自 latte-crew/bench/ 里实际运行的脚本。

总则

所有实验共用的做法

  • 一层一测。每个探针只经过它要测的那一层和它下面的层，尽量不让上层的开销混进来。比如测 vLLM 时直连 8101 端口，不经过 llama-swap 和 SSH。
  • 固定输入，重复取中位数。同一个输入重复 4–30 次，报告中位数，必要时附 p95 和最小值。中位数对偶发的网络抖动不敏感。
  • 客户端计时和服务端计数器互相印证。客户端用 time.perf_counter() 计时；服务端在请求前后各读一次 vLLM 的 Prometheus /metrics，取差值，得到这一个请求的预填充时间、解码时间、缓存命中 token 数。两边对得上，才采用。
  • 强制冷启动。需要测“不命中缓存”时，在提示开头放一个随机 uuid，让前缀缓存无法复用。
  • 固定输出长度。用 ignore_eos: true 和 max_tokens 让每次输出同样多的 token，TPOT 才能比较。
  • 独占 GPU。会改动 GPU 状态的实验（重启 vLLM、媒体模型）先拿 ~/latte-models/gpu.lock 上的 flock，和 media-bot、crewd 用同一把锁，避免 Bot 在测量中途切换模型。
  • 结果全部落盘。每个探针把一行 JSON 追加到 bench/out/*.jsonl，报告生成器 report/gen.py 只从这些文件读数，不手抄数字。

实验 1 · 连接层

SSH、MCP、scp 的延迟

脚本
probes/stack_probe.py，在 Mac 上运行
测什么
SSH 新建连接和复用连接；MCP 三种调用方式；复用连接下 scp 1 MB
重复次数
SSH 各 15 次，MCP 新会话和复用各 10 次，常驻会话 30 次，scp 8 次
输出
out/stack.jsonl：每项的 p50、p95、最小值和所有样本

计时的核心是一个通用函数：执行 n 次，记录每次的毫秒数，算中位数和 p95。

SSH 复用靠 OpenSSH 的 ControlMaster：先建一条后台主连接，之后的 ssh 通过同一个 socket 发起，不再握手。

MCP 不经过任何客户端库，直接把 JSON-RPC 的两行消息写进 crew.py mcp 的标准输入：一行 initialize，一行 tools/call。“新会话”每次都新开 SSH 并启动 MCP 进程；“常驻会话”只启动一次，之后每次只写一行调用、读一行结果，这和 Bot 持有 MCP 连接的方式一样。

SSH 隧道和 llama-swap 的开销不在这个脚本里测，而是在实验 3 里比较三条路径的 TTFT。

实验 2 · Agent 层

Claude Code、OpenCode 和 Kiro 网关的固定开销

脚本
bench/harness_probe.py（latte 上）；Kiro 部分是同样思路的内联脚本，结果在 out/kiro.jsonl
输入
同一句提示 reply with exactly: ok，让模型几乎不用生成，测到的就是 harness 自己的开销
重复次数
各 4 次，第 1 次含冷缓存，报告时取后 3 次的中位数
输出
out/harness.jsonl、out/kiro.jsonl

Claude Code 用 -p --output-format json 非交互运行，它输出的 JSON 里有 API 耗时和缓存读写 token。总时长减去 duration_api_ms，就是进程启动、插件和 MCP 初始化的时间。OpenCode 用 run --format json，从事件流里的 step_finish 读 token。两者都必须关闭标准输入，否则会一直等待。

Kiro 轮次：用服务端计数器拆分

Kiro 网关在 OpenCode 后面调用 vLLM，客户端看不到模型时间，所以在每一轮前后各读一次 /metrics，取六个计数器的差值：提示 token、缓存命中 token、生成 token、成功请求数、预填充秒数、解码秒数。

抓包代理：看清 Kiro 发给模型的内容

为了找出为什么每轮缓存命中都是 0，我写了一个只用标准库的反向代理，监听 8110，把请求原样转发给 llama-swap，并把每个 /chat/completions 的请求体写到文件。测试时临时把 OpenCode 配置里的 baseURL 改到 8110，跑两轮 Kiro，再改回去。流式响应用 read1 边读边写回，不影响客户端的流式体验。

拿到请求体后，用 vLLM 的 /tokenize 接口把两轮请求（messages 加 tools）各自转换成 token，找出第一个不同的位置。这一步给出了“第 184 个 token 分叉”和“重排后前 37,439 个 token 相同”这两个数字。

混合模型前缀缓存的对照实验

为了确认“中间改一处就完全不命中”是模型架构造成的，我用一个约 2.8 万 token 的合成提示做了三次请求：原始提示；只改中间一行；与第二次完全相同、只改结尾。每次都读 prompt_tokens_cached_total 的差值。结果分别命中 0、0、28,224 个 token。

实验 3 · 推理服务层

TTFT、TPOT、缓存命中和并发

脚本
bench/llm_probe.py <base_url> <out> grid|paths|conc [--metrics url]
服务配置
vLLM 0.32，Qwen3.8-27B AWQ，--max-model-len 65536 --max-num-seqs 2 --enable-prefix-caching --enable-mfu-metrics --kv-cache-metrics
请求参数
流式，temperature=0，ignore_eos=true，关闭思考（enable_thinking=false）
输出
out/llm-grid.jsonl、llm-conc.jsonl、llm-paths.jsonl、mac-paths.jsonl；GPU 同步采样 llm-gpu.csv

合成提示由重复的 Python 函数行组成，每行约 34 个 token，按目标长度拼接。开头的 tag 是随机 uuid，用来控制缓存能否命中。

TTFT 和 TPOT 的定义写在 stream() 里：TTFT 是发出请求到收到第一个内容 delta；TPOT 是第一个到最后一个 token 的时间除以 (输出 token 数 − 1)。思考内容的 delta 也算 token。同时记录相邻 token 间隔的 p99，用来发现卡顿。

服务端数据来自 /metrics。scrape() 把所有 vllm:* 计数器按名字加总（忽略直方图的分桶），run() 在请求前后各抓一次，把差值存进每行结果的 srv 字段。vLLM 在响应里返回的 cached_tokens 是空的，所以缓存命中只能从这里读。

三种模式

  • grid：7 档长度 × 4 次。每次先发一个新 uuid 的提示（冷），紧接着原样再发一次（命中）。
  • paths：同一个 500 token 的提示先发一次预热，再发 30 次。分别以 http://127.0.0.1:8101（直连 vLLM）、:8100（llama-swap）在 latte 上运行，以及在 Mac 上经 SSH 隧道 127.0.0.1:18100 运行。三者 TTFT 中位数之差就是每一层的开销。
  • conc：1–4 个线程同时发 4K 提示、300 个输出 token，每个线程的提示都不同。记录平均和最慢的 TTFT、平均 TPOT、总吞吐（所有输出 token / 墙钟时间）。

实验 4 · Kernel 与 GPU

Kernel 配置、profiler、MTP 和带宽上限

脚本
kprobe.py + run_kernel.sh（kernel 配置与 profiler），kprobe2.py + run_spec.sh（MTP）
编译器
conda 安装的 CUDA 13.0 nvcc，位于 ~/latte-models/cuda13；补了 lib64 → targets/x86_64-linux/lib 软链接，FlashInfer 的 JIT 才能链接到 libcudart
控制变量
每组配置都重启 vLLM；同一个探针；全程持有 GPU 锁
输出
out/kernel.jsonl、out/spec.jsonl、out/prof/{prefill,decode}/

驱动脚本先拿 GPU 锁，让 llama-swap 卸载当前模型，然后对每组配置：用指定的环境变量和参数启动 serve-qwen.sh，轮询 /health 直到就绪，跑探针，最后结束整个进程组。

探针本身包括：两档长度的冷预填充各 3 次（输出 2 个 token，只看 TTFT）；512 个 token 的解码 3 次；两路并发各 512 个 token。采样参数用 Qwen 推荐的 top_p=0.8, top_k=20，这样采样器才会真正走 top-k/top-p 路径。

torch profiler

vLLM 自带 profiler 开关。启动时传 --profiler-config，运行中用 POST /start_profile 和 /stop_profile 包住一个请求，profiler 会写出 Chrome trace 和一张按 kernel 汇总的表。我分别包住一次约 2 万 token 的预填充和一次 64 token 的解码。

报告里的分类图来自那张汇总表：只取叶子 CUDA kernel 的 Self CUDA 时间（排除 aten::、_C:: 这类 CPU 侧的包装，避免重复计算），再按名字归类：marlin 是 INT4 矩阵乘，耗时超过 0.5 ms 的 gemv 是 lm_head，flash 是全注意力，delta/gdn/conv1d 是线性注意力，以此类推。execute_context_0(0)_generation_1(1) 这一行的总时间除以调用次数，就是每个解码步的 GPU 时间（11.17 ms）。

MTP 推测解码

在同一个探针上加了一个更真实的负载：用 t5 题目的原文让模型写 1,500 个 token 的回答，开思考 3 次、不开思考 2 次。推测解码的接受率从 /metrics 的 spec_decode_num_draft_tokens 和 num_accepted_tokens 的差值算出。配置只差一个参数：--speculative-config {"method":"qwen3_5_mtp","num_speculative_tokens":k}，k = 1、2、3。

带宽上限是怎么算的

不读模型卡片，直接解析 safetensors 文件头：每个文件开头 8 字节是头部长度，头部 JSON 里有每个张量的字节范围。按名字把张量分到层、lm_head、嵌入、视觉编码器和 MTP，加总字节数。每生成一个 token 要读一遍层权重和 lm_head（嵌入只查一行），共约 16.7 GB；除以 RTX 5090 的 1,792 GB/s，得到 9.3 ms 的理论下限。

GPU 采样

最早用每秒一次的循环（gpu_trace.sh）；媒体实验需要更细，改用 nvidia-smi 自带的循环模式，每 250 ms 一行，直到停止文件被删除。

实验 5 · 媒体模型

Z-Image、Qwen3-TTS、Wan 和模型切换

脚本
bench/media_probe.py，配合 gpu_fast.sh 在后台采样
入口
全部通过 llama-swap（:8100）；Wan 的 multipart 接口走 /upstream/wan2.2-ti2v/v1/videos/sync
输出
out/media.jsonl（每次请求的起止时间与耗时）、out/media-gpu.csv

脚本一开始就拿 GPU 锁，和 media-bot 的行为一致。每个请求记录开始的 Unix 时间，之后用它把 GPU 采样对齐到具体某一次生成。

  • Z-Image：1024² 下 4、8、12 步各 4 次，再测 512²、768²、1344×768 各 3 次（8 步）。每张图用不同的 seed。
  • TTS：短、中、长三段中文各 4 次。返回的 wav 用 wave 模块读出帧数和采样率，算出音频时长；实时率 RTF = 合成耗时 / 音频时长。
  • Wan：25 帧跑两次（第一次含加载），之后 49 帧、121 帧，以及 49 帧下 15 和 50 步。
  • 切换成本：每个模型第一次请求的耗时减去之后同参数请求的中位数。因为 llama-swap 是互斥的，第一次请求包含了卸载上一个模型、加载权重、torch.compile 和 CUDA graph 捕获。

Wan 的阶段划分用的是 GPU 采样：在一次请求的起止时间内，利用率 ≥ 80% 的第一个和最后一个采样点之间算作去噪阶段，之前是排队和加载，之后是收尾（VAE 解码、搬运、编码）。去噪阶段内取功耗和 SM 时钟的中位数。

实验 6 · 协作实验

题目、三种方式、隐藏测试和打分

题库
collab/repo/（ledgerkit 初始仓库）、collab/tasks.json（6 道题）、collab/ref/（参考答案）
隐藏测试
collab/hidden/test_t1..t6.py，共 175 个用例，只保存在 Mac 上；参考答案先跑通全部用例，确认测试本身没错
额外边界测试
collab/extra/，由审查者发现的问题改写，共 4 个
驱动
collab/run.py <claude|local|codex>，在 Mac 上运行
打分
collab/score.sh + score_remote.py，结果在 collab/scored.json

仓库放在 latte 的 ~/development/ledgerkit，初始化成 git 仓库，crewd 会为每个作业创建独立的 worktree 和分支，所以 18 个作业互不干扰，最后每个分支对应一份答案。

驱动脚本

Claude 单独用 crew task --model sonnet；另外两种用 crew local。Codex 组先在 Mac 上对仓库的只读副本运行 codex exec --json --sandbox read-only，要求它只写计划不写代码，从事件流里取最后一条 agent 消息作为计划、取 turn.completed 的用量，然后把计划附在任务后面提交。

第二轮实验复用了第一轮的 Codex 计划，这样两轮之间唯一变化的是 Qwen 一侧的配置：

每个作业提交后每 10 秒查一次状态，结束时记录状态、审查结论、轮数、墙钟时间和花费。

每一轮都能单独打分

为了区分“第一轮就对了”和“审查后才改对”，我在 crewd 里加了一行：Qwen 每一轮提交后，把当时的 commit 追加到作业的 round_heads。

打分时隐藏测试才离开 Mac

所有作业结束后，score.sh 才把隐藏测试和额外测试拷到 latte 的 /tmp，跑完立刻删除。这样 Qwen、Claude、Codex 在答题时都不可能看到测试。

对每个 commit，用 git archive 导出到一个新的临时目录（不碰工作区），放入对应的隐藏测试，用 pytest 跑，从最后一行解析通过、失败、出错的数量。

token 和时间从哪里来

  • Claude：每次 Claude Code 运行的 result 事件，里面有输入、缓存写、缓存读、输出 token 和折算价格。
  • Qwen：OpenCode 的 step_finish 事件，每一步的输入、输出、思考 token。
  • Codex：turn.completed 里的 input_tokens、cached_input_tokens、output_tokens。
  • 阶段时间：crewd 的 ledger.jsonl，每个阶段（qwen-r1、local_reviewer-r1 …）一行，带秒数。

Qwen 的时间拆分

OpenCode 的事件都带毫秒时间戳：step_start、step_finish，以及每个 tool_use 的开始和结束时间。一步的时长减去其中工具的运行时间，就是模型时间；上一步结束到下一步开始之间是步间间隔。报告里“模型 95.9%、工具 0.8%、间隔 3.3%”就是这样把 28 次 Qwen 运行加总得到的。

审查发现的复现

每条 CHANGES 意见都在对应的 commit 上复现过。t2 用审查者给的输入直接调用函数；t4 和 t5 写成了额外的边界测试，再在三种方式的最终代码上统一运行。

数据到报告

数字是怎么进到报告里的

所有原始结果用 rsync 从 latte 的 ~/latte-bench/out/ 拉回 Mac 的 bench/out/，作业目录拉到 bench/out/jobs/。report/gen.py 读取这些文件，计算中位数和比例，用 charts.py、diagrams.py 生成内联 SVG，输出一个完整的 HTML。报告正文里的数字大多是 f-string 直接引用计算结果；少数从日志里人工读出的数字（例如带宽、profiler 每步时间）在本页对应的小节里给出了来源。

  • python3 bench/report/gen.py：生成分析报告
  • python3 bench/report/gen_methods.py：生成本页

已知局限

这些方法测不到或测不准的地方

  • 重复次数不多：微基准 4–30 次，协作实验每种方式每道题 1 次（第一轮因配置问题仅作参考）。
  • 连接层的数字包含 Tailscale 当时的网络状况；Mac 上的测量和 latte 上的测量没有做时钟同步，所以没有拼成同一条时间线。
  • Kiro 修复只用实验代理验证了 4 轮，没有在真实流量上长期观察。
  • Profiler 只抓了一次预填充和一次解码；分类是按 kernel 名字归的，个别 kernel 可能归错类。
  • Wan 收尾阶段的成分是根据功耗和利用率推断的，没有对照 vLLM-Omni 的阶段日志。
  • Claude 的花费是 Claude Code 报告的 API 折算价，实际用的是订阅额度。
